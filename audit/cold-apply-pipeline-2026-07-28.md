# Cold-apply pipeline — scope & staged plan (2026-07-28)

User's target (item 3, pivoted from browser-actuator C3): an end-to-end cold-apply flow —
job intake → tailored resume + cover letter → company/HR OSINT → cold mail (draft, then send on
explicit approval). Plus a dynamic resume page fed by GitHub projects + timestamped achievements.

This is a multi-session program, not one build. Most links depend on MCPs the user will connect. This
doc decomposes it into independently-shippable stages, marks buildable-now vs blocked, and fixes the
contracts so the pieces compose.

## Decisions locked (from the user)

- **Resume base:** a dynamic resume page. Projects auto-pulled via a **GitHub MCP**. Achievements are
  entered conversationally or typed, **timestamped** on capture. Resume + cover letter generated by a
  **"hiring-agent"** (an MCP/agent the user will name/connect — TREAT AS A DEPENDENCY, confirm identity).
- **OSINT / HR contact:** "whichever is best" → build a **pluggable contact-lookup seam**; default to the
  free `web_reach`/web lane, upgrade to Apollo/Hunter when a key is supplied. No hard dependency on a paid
  tool to boot.
- **Send:** **draft only**, never auto-send. Vishu queues a Gmail draft; the user reviews; sends only on
  an explicit "send the mails" instruction, or sends manually. (Fits the send-class F0 gate exactly.)

## What already exists in Vishu (ride it)

- **Gmail send/fetch** — `GmailConnector.send()` (SMTP, POP3), already send-class gated. Cold-mail
  delivery is built; needs `GMAIL_APP_PASSWORD`. For draft-only, prefer a Gmail *draft* (Composio Gmail
  `create_draft`) over SMTP send so nothing leaves until approved.
- **careerops MCP domain** — remote tools `careerops__discover_jobs / cover_letter / company_brief /
  skill_gap / duplicate_check`. Job intake + cover letter are already a tool surface once mounted.
- **MCP discovery + graceful degrade** — the `daily` module's pattern (find tools by name, no-op when
  absent) is the template for every MCP-dependent stage here.
- **Memory + automatic memory + IdentityProfile/DigitalTwin** — profile/facts feed resume personalization.

## Stages (cheapest-first; each independently shippable + mock-testable)

- **S0 — Achievements store (BUILDABLE NOW, zero external dep).** A timestamped achievements record the
  user adds by conversation/typing; resume-gen reads it. Mirrors DigitalTwin (atomic JSON in workspace).
  → shipped this session as the first brick.
- **S1 — Resume data model + GitHub projects (blocked on GitHub MCP).** A `resume` record = profile +
  achievements (S0) + GitHub projects (discovered via the GitHub MCP by name) + typed sections. Buildable
  as a data assembler now with a mock GitHub tool; live when the MCP is connected.
- **S2 — Resume + cover-letter generation (blocked on hiring-agent MCP).** Call the hiring-agent /
  careerops `cover_letter` with the S1 data + a job description. Confirm which MCP is the "hiring-agent".
- **S3 — Job intake (blocked on careerops/LinkedIn MCP).** `discover_jobs` / a job URL → structured
  {title, company, description}. Feeds S2 (tailoring) + S4 (OSINT target).
- **S4 — Company/HR OSINT (pluggable seam, default free lane).** {company} → {HR name, email, role}. Seam
  with a default `web_reach` implementation; Apollo/Hunter adapter when a key exists.
- **S5 — Cold-mail draft + approve (rides GmailConnector/Composio draft).** Compose {resume, cover letter,
  HR contact} → a Gmail **draft**; surface for review; send ONLY on explicit approval. Never auto-send.
- **S6 — Dynamic resume page (frontend).** Renders the S1 resume model; edit typed sections/achievements.
  Frontend work, sequence after the data stages are real.

## Dependencies to confirm / connect (user action)

1. **"hiring-agent"** — which MCP/agent is this? (careerops, or a separate one?) Blocks S2.
2. **GitHub MCP** — connect it (`vishu connect …`) so projects import. Blocks S1 projects.
3. **Job platform MCP** (LinkedIn/careerops) — blocks S3.
4. **OSINT key** (optional) — Apollo/Hunter key upgrades S4 above the free lane.
5. **Gmail** — `GMAIL_APP_PASSWORD` (SMTP) or Composio Gmail (draft). Blocks S5 live.

## Recommended build order

S0 (done) → S1 assembler (mock GitHub) → S4 OSINT seam (free-lane default) — these three are buildable
and mock-testable without waiting on the user's MCPs. S2/S3/S5 wire in as their MCPs connect. S6 (page)
last. Each stage green-gated + committed; live verification is user-run (mock-only per user choice).
